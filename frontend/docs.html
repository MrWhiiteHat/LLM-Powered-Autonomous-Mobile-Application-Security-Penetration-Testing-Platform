1. System Architecture & Processing Boundary

HOST-CONFINED IPC

The Mobile Security Agent (MSA v2.0) is an autonomous, multi-phase mobile application security penetration testing platform engineered with localized Retrieval-Augmented Generation (RAG) and cognitive LLM reasoning. Unlike conventional Static Application Security Testing (SAST) tools that rely strictly on brittle regular expression pattern-matching, MSA v2.0 correlates static AST data flow, manifest configurations, dynamic runtime instrumentation, and an authoritative security knowledge base.

🔒 Host-Confined Processing Boundary & Compliance Guarantee

MSA v2.0 guarantees that 100% of binary decompilation, AST extraction, RAG embeddings, and LLM inference execute strictly within the local host machine's RAM and localhost socket. No decompiled bytecode, proprietary secrets, network endpoints, or audit prompts are ever transmitted to third-party cloud APIs. This architecture provides full verifiable compliance with GDPR Article 28 (data sovereignty), HIPAA Security Rule 45 CFR Part 164, and PCI-DSS v4.0 Requirement 6.3.

2. The 10-Phase Autonomous Pipeline

STRICT JSON CONTRACTS

MSA v2.0 executes an orchestrated sequence of 10 specialized auditing modules. Each phase is decoupled through structured JSON contracts and isolated try-except boundaries: if dynamic instrumentation is offline due to lack of a physical test device, the pipeline gracefully falls back to static AST taint analysis without pipeline failure.

Phase 1: Binary Reconnaissance & Cryptographic Integrity

file_handler.py

Computes multi-digest checksums (SHA-256, SHA-1, MD5), validates Android v1-v4 APK signing schemes, verifies certificate expiration and CA trustworthiness, parses min/target SDK versions, and assigns target size tiers.

Phase 2: Static Dissection & Manifest Attack Surface

static_analysis.py

Invokes aapt dump xmltree to audit binary XML, identifying 32 dangerous runtime permissions, exported Components (Activities, Receivers, Services, ContentProviders) lacking signature protection, android:debuggable="true", and android:allowBackup="true" flags.

Phase 3: Reverse Engineering & AST Construction

reverse_engineering.py

Decompiles DEX bytecode into Smali and Java source trees via APKTool 2.9+ and JADX 1.5+. Constructs Abstract Syntax Trees (AST) using javalang, extracts REST/WebSocket API endpoints, and identifies embedded high-entropy cloud credentials.

Phase 4: Storage Security & Data Leakage Analysis

storage_analysis.py

Audits local sandbox storage: checks for deprecated MODE_WORLD_READABLE flags in SharedPreferences, unencrypted SQLite database schemas, SQL raw query injection vectors, and insecure public external storage writes.

Phase 5: Network Security & Transport Layer Trust

network_analysis.py

Evaluates network_security_config.xml, detects cleartext HTTP transmissions (usesCleartextTraffic="true"), audits custom empty TrustManager implementations, flags AllowAllHostnameVerifier, and identifies weak SSL/TLS protocols.

Phase 6: API Security Testing (OWASP API Top 10)

api_testing.py

Probes extracted REST/GraphQL endpoints for Broken Object Level Authorization (BOLA), unauthenticated administrative interfaces, Broken Function Level Authorization (BFLA), server-side request forgery (SSRF), and injection flaws.

Phase 7: Dynamic Runtime Instrumentation

dynamic_analysis.py

Instruments running target applications via Frida 16.x hooks and ADB. Intercepts Java cryptographic APIs (javax.crypto.Cipher.init) to detect static IVs, monitors file I/O operations, and bypasses root detection and certificate pinning.

Phase 8: RAG Vulnerability Mapping & Semantic Triaging

vulnerability_mapper.py

Enriches candidate findings using the dual BM25 + TF-IDF RAG engine with Reciprocal Rank Fusion ($k=60$). Prompts the local LLM Cognitive Auditor to prune false alarms by assessing data-flow reachability and developer defensive checks.

Phase 9: Automated Risk Scoring (CVSS v3.1)

risk_assessment.py

Calculates precise CVSS v3.1 vector strings and base scores based on Attack Vector (AV), Attack Complexity (AC), Privileges Required (PR), User Interaction (UI), Scope (S), and Confidentiality/Integrity/Availability impact metrics.

Phase 10: Multi-Format Report Generation

report_generator.py

Compiles machine-readable JSON artifacts and rich, self-contained HTML reports via Jinja2 templates, embedding copy-pasteable Java/XML remediation diff patches for instant engineering handoff.

3. Dual-Retriever Hybrid RAG Engine

RRF FUSION (k=60)

Conventional LLM scanners either suffer from hallucinations or ungrounded outputs. MSA v2.0 solves this via an in-memory dual retrieval-augmented generation engine indexing 2,075 authoritative security controls across 62,710 custom tokens.

1. Dual In-Memory Retrievers

  • Okapi BM25: Probabilistic keyword matching optimized for rare security terms ($k_1 = 1.5, b = 0.75$).
  • TF-IDF Vector Space: Cosine similarity with sub-linear term frequency scaling for semantic matches.
  • Zero DB Overhead: Pre-tokenized inverted indexes reside directly in RAM, achieving sub-millisecond retrieval.

2. Reciprocal Rank Fusion (RRF)

Combines independent rankings from BM25 and TF-IDF without score scaling bias:
RRF(d) = Σ [ 1 / (k + r_m(d)) ] with constant k = 60.
Guarantees that high-consensus documents receive top priority while outlier false positives are filtered out.

3. In-Memory Knowledge Graph (34 Taxonomy Edges)

A directed taxonomy graph bidirectionally maps high-level OWASP Mobile Top 10 (M1–M10) categories to granular MITRE CWE identifiers (e.g., M1 → CWE-926, CWE-749; M2 → CWE-312, CWE-922, CWE-276; M5 → CWE-327, CWE-326). When a candidate finding is flagged, graph expansion traverses adjacent parent-child nodes to provide complete context to the LLM.

🧠 LLM Cognitive Auditor for Noise Suppression (89.2% NSR)

Static regex tools flag inactive or benign patterns (such as dummy testing keys or dead code). MSA v2.0 prompts the local Ollama LLM (Qwen2.5-Coder 1.5B / Llama-3) with the candidate finding, enclosing AST snippet, and retrieved RAG context. The model evaluates whether the flaw is reachable or mitigated by developer defensive controls. In our controlled 160-target benchmark, this pruned 25 out of 28 raw alarms, achieving an 89.2% false-positive noise reduction rate.

4. Vulnerability Triage & Actionable Remediation

DEVELOPER CODE DIFFS

MSA v2.0 provides developer-actionable remediation diffs rather than generic advisory text. Below are standard secure coding remediation patterns generated across the platform:

1. Application Debuggable Flag (CWE-215 / MASVS-RESILIENCE) — CVSS 8.4 [HIGH] CRITICAL EXPLOIT

Vulnerability: android:debuggable="true" enables JDWP debuggers to attach via USB and inspect memory variables. 

<!-- Remediated AndroidManifest.xml -->
<application
    android:allowBackup="false"
    android:debuggable="false"
    tools:replace="android:debuggable,android:allowBackup">
</application>
2. Cleartext HTTP Traffic (CWE-319 / MASVS-NETWORK) — CVSS 6.5 [MEDIUM] MITM VECTOR

Vulnerability: Permitting plaintext HTTP transmissions exposes credentials to rogue Wi-Fi access points. 

<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>
</network-security-config>
3. Exported Component Lacking Signature Permissions (CWE-926 / MASVS-PLATFORM) — CVSS 7.1 [HIGH] UNAUTH ACCESS

Vulnerability: Exported Activities or Services can be invoked by rogue apps to trigger unauthenticated actions. 

<!-- Restrict exported components in AndroidManifest.xml -->
<activity
    android:name=".AccountTransferActivity"
    android:exported="false" />
4. Insecure Cryptography / Broken Ciphers (CWE-327 / MASVS-CRYPTO) — CVSS 7.5 [HIGH] WEAK CIPHER

Vulnerability: Using DES or AES/ECB allows deterministic ciphertext replay and ECB penguin attacks. 

// Modern AES-GCM Authenticated Encryption with Dynamic IV

byte[] iv = new byte[12];
new SecureRandom().nextBytes(iv);
GCMParameterSpec spec = new GCMParameterSpec(128, iv);
cipher.init(Cipher.ENCRYPT_MODE, secretKey, spec);

Statistical Significance & McNemar Paired Contingency Tables

To confirm that measured improvements are statistically significant, McNemar's test with Edwards' continuity correction was performed across the 64 canonical comparative targets:

  • MSA v2.0 vs. MobSF: Paired outcomes: 37 both correct (a=37), 23 MSA correct/MobSF wrong (b=23), 1 MSA wrong/MobSF correct (c=1), 3 both wrong (d=3).
    χ² = (|23 - 1| - 1)² / 24 = 18.38 (exact two-tailed binomial p = 2.98 × 10⁻⁶ < 0.0001).

    χ² = (|10 - 2| - 1)² / 12 = 4.08 (exact binomial p = 0.0386 < 0.05).
